# Stage ② Synthesis Pipeline — Report

**Date:** 2026-08-29
**Deck proved:** `w01-game-first-contact` (9 slides, 8,776 characters)
**Pipeline location:** `~/code/fivex/mod_node/modules/lecture/` (`eleven-labs-client.ts`, `synthesize-lecture.ts`)

## What changed from the rejected first attempt

The prior `synthesize-lecture.ts` / `eleven-labs-client.ts` sent an entire deck as one
`/with-timestamps` request on `eleven_multilingual_v2` (forced by v3's 5,000-character
request cap) and derived spans from character-level alignment. Both files were rewritten
in place to implement spec §16 exactly:

- Per-**slide** synthesis against the plain endpoint `POST /v1/text-to-speech/{voice_id}`
  (no timestamps endpoint), model `eleven_v3`, voice `V7cskzCG9mkMsOof0Nmn`.
- Fixed `voice_settings`: `stability 0.3, similarity_boost 0.7, style 0.5,
  use_speaker_boost true`. No `speed` field sent.
- Every slide's raw clip is written to disk **immediately** on a successful response,
  before any further processing.
- Post-process: `ffmpeg -filter:a "atempo=1.2"`, re-encoded to `libmp3lame` so every
  intermediate clip carries an accurate LAME header for duration reporting.
- Duration is measured with `ffprobe` **on the stretched clip**, never the raw clip and
  never estimated from words-per-minute.
- Concatenation decodes every stretched clip + a shared silence clip to PCM via an
  `ffmpeg -filter_complex ... concat=` chain and re-encodes once — not a stream-copy
  concat demuxer — so per-clip encoder padding from separate encode calls can't drift
  the timeline.
- `audio_span` is computed from the same cumulative (duration + gap) arithmetic the
  concatenation itself performs, so spans and the file agree by construction, not by
  coincidence.
- Any slide whose **stretched** clip already exists on disk is skipped entirely (no API
  call). A slide with a cached raw clip but no stretched clip yet is re-stretched from
  the cached raw, not re-synthesized.
- `script_hash` in `audio{}` is copied verbatim from `source.script_hash`; `generated_at`
  is generated by the pipeline itself (never accepted as input) — closing the validator-
  divergence risk noted in spec §8/§14 item 3, since the value is guaranteed to be a real
  ISO-8601 timestamp instead of externally supplied data.

## Gap between slides

**350 ms** of digital silence (a single `anullsrc` clip, generated once per deck and
reused). Chosen because it's audible as a breath/beat between topics without producing
dead air — long enough that the previous sentence's cadence completes, short enough that
back-to-back short slides (e.g. slide 1 → 2, both under 15 s) don't feel like the deck
stalled. It's inserted **between** slides only — no leading or trailing silence on the
deck as a whole.

**WPM cluster: min 174, median 204, max 238.** This does **not** cluster near the
spec's calibration figure of 146 wpm (raw v3 122 wpm × 1.2 stretch) — every slide runs
faster, by roughly 20–90 wpm, and the scatter (174–238, a 64-wpm spread) is wider than a
single consistent delivery rate would produce. Read together with the rest of the
evidence below, this does **not** look like a technical failure (no retries, no mismatched
clips, contiguous non-overlapping spans, span sum agrees with the file to 1 ms, ajv
passes) — it looks like a genuine difference in delivery pace between per-slide requests
and the single passage the settings were calibrated on. Flagging per the brief's
instruction to follow the API's actual behavior and report deviations rather than tune
around them: **the instructor should listen to this deck before treating 146 wpm as the
expected pace for per-slide synthesis** — the approved settings were validated on one
passage sent as part of a longer bake-off, not on short, request-isolated slide text,
and pacing may simply run faster without a preceding paragraph's context per request.
