## Summary

CS 3540 is rebuilt around a single claim: **a complete game is now one prompt away, so the
scarce skill is no longer implementation — it is specification and verification.**

The evidence is local. `~/code/3dscroller` contains two complete, deployed, tested
Age-of-Empires-style RTS builds — one Dart/Flutter GPU (4,892 LOC), one TypeScript/three.js
(3,954 LOC) — produced from the same prompt plus six answered questions. They converged
independently on the same architecture. That convergence is the course's founding exhibit
and its first assignment, not its capstone.

The course therefore has three tracks matching three tenets:

| Tenet | Track | Shape |
|---|---|---|
| **Play** — history, fun, story, mystery | Codex | devlog + *My Favorite Game* talk |
| **Craft** — 2D, 3D, procgen, AI, netcode | Spec + Generator | shared class spec, owned by section |
| **Soul** — the 11 Pillars, archetypes, AI SDLC | Forge | 9 artifacts, applied to game dev |

All three converge on **the game**, which carries 42% of the grade.

## 2. The three-act arc

### Act I — The Baseline (Weeks 1–3)

Students reproduce the 3dscroller experiment: a complete game from one prompt. Deliverable is
the working game **plus a failure analysis** — where did it break, what could you not change,
why. This establishes both the power and the ceiling, and motivates everything after it.

Closes with **The Pitch**: the game concept each student grows all term.

### Act II — The Spec (Weeks 4–9)

Foundational evaluation of real engines (three.js, Godot, Bevy, Unity, Unreal, LÖVE, Phaser)
yields **the intersection, not the ideal**. The class co-authors one engine spec; each student
owns sections. The generator loop starts and runs weekly for the rest of the term.

### Act III — The Studio (Weeks 10–16 + Finals)

Games built on the engine, with the full generative pipeline and multiplayer. Solo or team.
Seven weeks of build time, matching the 42% weight.

The spec does not stop at Week 9 — generator runs and divergence fixes continue weekly through
Week 16.

## 3. The engine spec

### 3.1 Guiding rule

> **The simulation must not know that rendering exists.**

Inherited from `3dscroller`, where `test/sim/purity_test.dart` enforces it by walking
`lib/sim/**` and failing on any `import`/`export` of `package:flutter`, `dart:ui`, or
`package:flutter_scene`. CS 3540 reproduces that gate in TypeScript.

Pear reinforces it architecturally: the renderer is a sandboxed Chromium context that can only
reach the network through the preload bridge, which carries commands. The convention becomes a
process boundary.

### 3.2 The three seams

Every seam is Strategy + dependency injection. All three keep the sim pure and make headless
grading possible.

| Seam | Implementations |
|---|---|
| `Renderer` | 2D · 3D (WebGL2) · **headless** (what the grader runs) |
| `Transport` | Local/hotseat · **Pear** (Hyperswarm hot path, Hypercore durable log) · WebRTC (optional) |
| `Generator` | procedural fallback · local Ollama · Ollama Cloud · `llm.uvucs.org` |

### 3.3 The unifying insight

**Anything nondeterministic enters the simulation as a recorded command.** Player input, remote
peer input, and LLM output all use one seam. Record the model's response into the command log
and replay stays bit-identical even though the original run was not — exactly how lockstep
netcode handles a remote player.

This collapses three catalog requirements (networking, AI game programming, compelling
storylines) into one architectural seam.

### 3.4 Determinism and the state hash

Ported from `lib/sim/world.dart`: an FNV-1a world-state hash that **quantizes before hashing**
(`(pos.x * 1000).round()`, `(hp * 10).round()`) folded over entity id, kind, owner, position, hp.

Quantization is what lets the hash survive a language boundary — raw IEEE floats will not agree
across runtimes. The hash serves four purposes at once: desync detector, replay verifier,
conformance oracle, and proof an LLM NPC did not corrupt the sim.

### 3.5 Section list

**Instructor-owned core** (not assigned; authored Weeks 1–4):

- `S00` Overview, glossary, seams, conformance vector format
- `S01` Time and the fixed-timestep loop
- `S02` Determinism: seeded RNG and world-state hash
- `S03` Command model and command log

**Student-ownable** (15 sections; assign 1:1, instructor absorbs surplus sections, students pair
on heavy sections if enrollment exceeds 15):

| | Section | Catalog requirement served |
|---|---|---|
| `S04` | Transform hierarchy and scene graph | design & implementation of game software |
| `S05` | Entity and component store | design & implementation of game software |
| `S06` | Event bus and messaging | design & implementation of game software |
| `S07` | Input abstraction and mapping | — |
| `S08` | Asset handles, caching, provenance manifest | procedural asset generation |
| `S09` | Renderer seam and 2D backend | **two-dimensional graphics** |
| `S10` | 3D backend (WebGL2) | **three-dimensional graphics** |
| `S11` | Collision and spatial partition | — |
| `S12` | Pathfinding, navigation, steering | AI game programming |
| `S13` | Game AI: FSM, behavior trees, utility | **AI game programming** |
| `S14` | Procedural generation | **procedural generation of assets** |
| `S15` | Narrative: dialogue graph and quest state | **compelling storylines** |
| `S16` | Generator seam: LLM and asset providers | — |
| `S17` | Transport seam: Local and Pear | **network programming for multiplayer** |
| `S18` | Audio and procedural music | procedural generation of assets |

Principles of game design are served by the Codex track, not a spec section.

### 3.6 Constraints on a section

- **Must be implementable in a second language.** A TypeScript dump fails this on its face, and
  it keeps the cross-language conformance path open. This is the primary guard against a student
  writing code and calling it a spec.
- **Must state behavior, invariants, and acceptance criteria**, not an implementation.
- **Must ship conformance vectors** — JSON, with expected state hashes.
- **Dependency order matters.** `S01`–`S03` are upstream of everything; `S15`, `S17`, `S18` are
  leaves. Instructor owns the upstream spine.

## 4. The generator and the divergence metric

### 4.1 The loop

Builds are produced by a **scheduled Claude agent on the instructor's account**, not by students.
It runs the night before each class session (Mon and Wed), so studio time always opens with fresh
divergence data.

```
K independent builds from spec@SHA   (K = 3 to start; raise if the sample is noisy)
  → run conformance vectors on each
  → compare state hashes
  → divergence report        → committed to engine-spec/reports/
  → promote the modal build  → committed + tagged in uvucs3540/engine
```

Students still run the generator, but **narrowly and locally**, while iterating on the section
they own:

```bash
./generator/build.sh --section S09    # fast, focused, no quota concern
```

### 4.2 Promotion gate

The **modal build** — the one whose state hashes agree with the most others — is promoted,
versioned, and tagged. Version ties the engine to the spec commit that produced it:

```
v2026.10.13+spec.a3f9c21
```

**A section whose builds never reach consensus cannot be promoted.** The engine does not ship
until the prose is unambiguous enough that independent implementations agree. Specification
failure is a release blocker, not a rubric comment.

Games pin a tag and upgrade deliberately. The reference engine the students' games run on is
therefore generated from the students' own spec — if they specify badly, they feel it in their
game.

### 4.3 The metric

For each conformance vector owned by a section, compute agreement across the K builds.

| Builds agree with each other? | Match the vector? | Diagnosis |
|---|---|---|
| Yes | Yes | Section is well specified |
| **No** | — | **Ambiguous prose** — the owner's writing is underdetermined |
| Yes | **No** | **Wrong vector** — the section's test encodes a claim the prose does not make |

`section_score = mean(agreement(v) for v in section.vectors)`. Reported twice weekly; the number
climbs as the prose improves.

Cron-produced builds give a **more controlled** sample than student-run builds would: environment
is held constant, so divergence is attributable to the prose rather than to someone's laptop.

### 4.4 The cron is a Module 4 artifact

An unattended scheduled agent committing code with no human in the loop is threat #5 of the
training's threat model. It is built accordingly, and shown to the class as the worked example:

- `--append-system-prompt` declaring scope, forbidden operations, and stop conditions
- Narrowed tools
- A `PreToolUse` hook blocking any write under `spec/` or `conformance/` — the generator may
  produce `out/` and nothing else
- Attributed commits

> **The generator must never be able to edit the spec it is tested against.** Without that hook
> the measurement is circular: an agent that can weaken a conformance vector will, and the
> divergence metric silently reports success.

### 4.5 Failure containment

- Sections sit behind interfaces, so a broken section fails its own vectors rather than the build.
- Instructor holds **reference sections** in reserve; a section still divergent after two revision
  cycles gets replaced so the class is never blocked.
- Instructor also holds **reference implementations** per act, released after each act's deadline.

## 5. Assets and generation

### 5.1 Three rings

Every modality needs a Ring 0 that works with no server, no GPU, and no network.

| Modality | Ring 0 — always works | Ring 1 — local | Ring 2 — class server |
|---|---|---|---|
| Dialogue / NPC | authored fallback lines | Ollama, 1–4B instruct | `llm.uvucs.org`, Ollama Cloud |
| Images | **procedural textures in-engine** | FLUX.1-schnell, Draw Things | — |
| 3D meshes | **primitives assembled in code** | TRELLIS (MIT), Hunyuan3D-2 | GPU box (see risks) |
| Music | **Web Audio procedural score** | ACE-Step, MusicGen-small | — |
| Speech | **Kokoro-82M in-browser** (Apache-2.0), `speechSynthesis` | Piper (MIT) | — |
| Video | **in-engine cutscene system** | — | optional, rate-limited |
| Network | local/hotseat | — | **Pear — no server at all** |

Procedural textures, procedural music, and primitive meshes are not compromises — they are the
catalog's "procedural generation of assets" requirement, and `ts_game/README.md` already proves
a shipped RTS needs no art assets at all.

### 5.2 Generation is build-time and manual

`chat.uvu.edu` (Gemini 3.1 Pro, ChatGPT, Claude, Copilot) exposes **no API**. All image and 3D
generation is therefore: generate in the chat UI, download, commit, record in the manifest. No
runtime asset generation anywhere in the course.

### 5.3 Provenance manifest

`assets/MANIFEST.json` — one entry per generated asset:

```
{ "path", "modality", "model", "prompt", "seed", "date", "license", "cost", "phase" }
```

`phase` is `build` or `runtime`. The manifest is simultaneously the attribution policy, the cost
ledger, the supply-chain lesson (Module 4 threat #4), and a greppable autograded artifact.

### 5.4 Claude Pro vs. runtime

**Claude Pro is not API access.** Pro covers claude.ai and Claude Code; programmatic calls bill
separately.

| | Covered by Claude Pro |
|---|---|
| Build-time text generation — lore, quests, balance tables — via `claude -p` | Yes |
| Runtime NPC dialogue in a shipped game | No — class endpoint or local Ollama |

The CS 3660 page `llm-endpoint-setup.md` currently states the outage fallback is "Claude API
(your Claude Pro account)." **That is incorrect and should be corrected in CS 3660 as well.**

### 5.5 Grade the seam, not the provider

The `S16` conformance vector asserts that **with every remote provider unreachable, the game still
runs and degrades visibly.** Kill the endpoint, run the vector, the game must still play.

This is the global standard's rule 8 (no silent error swallowing) as an executable test, and it
makes an Ollama free-tier quota exhaustion on showcase night survivable. Ollama's free tier
limits are unpublished and GPU-time based; no graded deliverable may depend on them.

## 12. Out of scope

- Diffusion video as a required deliverable — replaced by the in-engine cutscene system.
- Authoritative-server multiplayer — P2P lockstep has no authority; "why authoritative servers
  exist" is taught by demonstrating what is lost without one.
- Quizzes and separate weekly reflections — the devlog carries lecture accountability.
- Peer scoring.
- Cross-language conformance as a required track — it remains available as extra credit, since the
  spec is authored to be language-neutral.
- Unity, Unreal, and Godot. The course teaches the principles those engines exist to hide.

## 13. Success criteria

1. Every catalog requirement traces to a spec section and a shipped demonstration (§3.5).
2. Every student ships a playable game with generated assets, an LLM-driven narrative element,
   and working multiplayer.
3. Mean section agreement climbs measurably between Week 6 and Week 16.
4. Every game still runs with all remote providers unreachable.
5. No student is blocked by another student's section for more than two revision cycles.
