## 1. Course identity

CS 3660 *Advanced Web Development* at UVU. The 2026 redesign is built on two pillars not present in 2025:

1. **Vernacular as foundation.** In an LLM-mediated industry, fluency in the vocabulary of software engineering — Agile Manifesto v2 (Hunter 2024), GoF design patterns (refactoring.guru/design-patterns/catalog), Enterprise Integration Patterns (enterpriseintegrationpatterns.com), the Perfect Framework (Hunter 2024), and Claude Code's own capability vocabulary (`claude-code-capabilities.md`) — *is* the prerequisite for productive collaboration with AI. Vocabulary is the foundation of the class, surfaced in every lecture, every artifact, every presentation, and verified by the LLM grader.
2. **Claude Pro is the textbook.** No paid book. Each student maintains a Claude Pro subscription and learns to leverage Claude Code as their primary development environment. Mastery is demonstrated by building Claude Code extensions (skills, subagents, hooks, MCP integrations, plugins) — not by reading about them.

The course retains "Advanced Web Development" coverage requirements: HTML/CSS/JS, frameworks, server-side, databases, REST/GraphQL/messaging, realtime web, security, accessibility, deploy/CI-CD. These live in a dedicated **lecture spine** that runs parallel to project work.

Instructor: Michael Hunter (`hunterino` on GitHub, 10207885@uvu.edu).

## 5. Track 1 — Coverage spine (lectures)

Async YouTube lecture per week, plus live Mon/Wed discussion that *applies* the lecture content to current sprint work. Lectures are recorded once and reused across years; live discussion is what justifies attendance.

**Vernacular layering rule**: every lecture, while presenting an architectural concept, names that concept with all four labels — its GoF pattern (if any), its EIP (if any), its Perfect Framework concern, and its Claude Code capability analog (if any). Example: "Today's `useEffect` cleanup function is a Disposer pattern, an EIP Message-Endpoint with cleanup, the Perfect Framework's *Workflow → Compensate* concern, and resembles Claude Code's `Stop` hook."

**Lecture sequence** (13 lecture weeks; W14 reserved for finals):

1. Course intro · Agile Manifesto v2 · Perfect Framework tour · vernacular tour
2. HTML/CSS/JS refresh · Job Pack kickoff · class LLM endpoint primer
3. Frameworks survey (React, Vue, Svelte, Flutter-web) · GoF Creational patterns
4. Node, REST, basic auth · GoF Structural patterns
5. SQL + document stores + DB versioning · GoF Behavioral patterns
6. Enterprise Integration Patterns Part 1 — channels, message construction
7. Enterprise Integration Patterns Part 2 — routing, transformation · state charts (XState)
8. Realtime web — MQTT, WebSockets, GraphQL subscriptions
9. PRPL pattern, service workers, offline-first
10. Perfect Framework deep-dive — scale, i18n, accessibility, RBAC
11. Advanced web platform — WebRTC, USB, Bluetooth, Camera
12. PKI · security review · OWASP top 10 in 2026
13. CI/CD · observability · production-readiness

**Weekly reflection** (300 words max, due Sun 23:59 MT each week): "Pick one term from this week's lecture that you used in your project this week. Where did you use it? What was the alternative you considered? Why this one?" LLM-graded for correct usage of vocabulary; minimum bar is "vocabulary used correctly in context."

## 6. Track 2 — Team sprints

Teams of 4 (or 3 if class size is short), reshuffled each sprint. Repos provisioned under `uvucs3660/project{N}_team{M}_summer_2026` via `examples/gittools/repo_gen.dart`.

**Team generation (no-repeat invariant).** Teams are computed by the class team-generator such that **no two students share a team in more than one sprint** (max-coverage scheduling). With three 4-person sprints and a class size of ~16–24, the constraint is satisfiable and yields each student working with up to 9 distinct classmates over the term. The instructor's existing tool (`examples/gittools/`) implements the partitioning; the 2026 implementation must verify the no-repeat invariant before publishing teams (the 2025 `projects.json` did not fully enforce it). Algorithm runs once per sprint, after the prior sprint's demos, consuming the roster of students who completed all 5 W1 onboarding assignments. Late-onboarders are added in subsequent sprints if a slot opens.

### Sprint 1 — Job Pack (4 weeks, 10% of grade)

**Brief**: Build a single-user web application that takes a pasted job description and a pasted candidate profile, and produces three artifacts:
1. Customized **résumé PDF** matched to the job
2. Customized **cover letter PDF** addressed to the company
3. **One-page company-fit infographic** (SVG or PNG) summarizing pros/cons of working there

**Mandatory technical requirements**:
- LLM backend selectable via Strategy pattern across at least two of: hosted class Ollama (default), Claude API, raw local Ollama. Switching backend must require zero code changes — config only.
- Drafts persist server-side; user can save, re-open, edit, and compare ≥2 drafts for the same job.
- Deployable: frontend on Netlify or `uvucs.org`, backend either embedded (single-process) or split.
- Inputs are pasted text only — no scraping LinkedIn/Indeed (TOS).
- Authenticated calls to the class LLM endpoint use the student's API key from a `.env` file (never committed).

**Vernacular rubric**: presentation must explicitly name and explain ≥2 GoF patterns used, ≥1 EIP used (Pipeline is the easy one), and ≥2 Perfect Framework concerns addressed. LLM grader verifies correct usage, not just name-dropping.

**Stretch (rubric bonus, capped at +10%)**: multilingual résumé output (i18n), accessibility audit pass (WCAG AA), automated regression test suite.

**Demos**: Mon Jun 1, in-class. 12-minute live demo + 3-minute Q&A per team.

### Sprint 2 — Messaging-rich system (4 weeks, 15% of grade)

**Brief**: Build a multi-component system in which different components communicate via messaging. Topic open-ended. Plausible directions: real-time multiplayer game, collaborative whiteboard, IoT dashboard, multi-agent simulation, live event-driven feed.

**Mandatory technical requirements**:
- ≥3 distinct EIPs implemented (one of which must be Publish-Subscribe via MQTT or WebSockets). Examples: Message Router, Content Filter, Content Enricher, Aggregator, Resequencer, Splitter, Message Translator.
- ≥1 explicit state chart (XState or hand-rolled) governing a non-trivial workflow.
- Persistence layer with audit trail / point-in-time history (Perfect Framework: audit trails).
- LLM-as-a-service component allowed but not required; if used, must consume the class endpoint via the Strategy pattern from Sprint 1.

**Vernacular rubric**: presentation must explicitly name and explain ≥3 EIPs, ≥2 GoF patterns, the state-chart structure (states, events, transitions, guards), and ≥3 Perfect Framework concerns addressed.

**Demos**: Mon Jun 29, in-class. 15-minute live demo + 5-minute Q&A per team.

### Sprint 3 — Capstone (5 weeks, 25% of grade)

**Brief**: Open. Teams pitch and deliver a system of their choosing.

**Mandatory technical requirements** (rubric-enforced):
- Must address a Perfect Framework concern not covered in Sprints 1–2 (i18n, accessibility, offline, audit trails, RBAC, observability, internationalization, units of measure, etc.) — explicitly named in the pitch.
- Must use ≥1 advanced web-platform technology not used in Sprints 1–2 (WebRTC, USB, Bluetooth, Camera, PWA/service-worker offline, WebGPU, WebAssembly).
- Must ship with a working CI/CD pipeline (GitHub Actions or equivalent) that runs tests on PR and deploys on merge to main.
- Must include observability hooks (structured logs at minimum; bonus for metrics or tracing).

**Pitch checkpoint**: Mon Jul 6 (W10), in-class. Each team presents a 5-minute pitch covering the chosen scope, the targeted Perfect Framework concern, the advanced platform technology, and the team's risk register. Instructor approves or course-corrects.

**Final demos**: Wed Aug 5, in-class. 20-minute live demo + 10-minute Q&A per team.

### Track 2 grading (all sprints)

LLM grader inputs per sprint, per team:
- Team repo URL + final commit SHA tagged with `sprint-{N}-final`
- `git log --pretty=fuller --numstat` for the sprint window, scoped per author
- Per-member PR list (created, reviewed, comments authored)
- Presentation video transcript (auto-generated)
- Per-member individual reflection (≤500 words: "what I built and which patterns I used"), due 24h after demo
- The sprint-specific rubric

LLM grader produces per-member individual grade out of 100, with a written rationale citing specific commits/PRs/reflections. Instructor reviews + can override (logged).

**LLM grader rationale writing style** (FERPA-driven; see Section 10):
- Reference *work*, not other students. Cite commits, PRs, files, and the rubric criterion — never another team member's score, ranking, or relative performance.
- Describe the rated student's contribution in scope language ("your work was concentrated on the persistence layer"), not comparative language ("you were the strongest" / "below the team average").
- Use roles, not names, when describing surrounding work ("the integrator handled deploy", not "Alice handled deploy").
- The rationale must be safe to forward to a teammate without revealing FERPA-protected information about other students.

## 7. Track 3 — Individual Claude Code artifacts

Five biweekly artifacts. Each demonstrates one Claude Code capability from `claude-code-capabilities.md`. Each is graded on a fixed rubric: works as described, uses CC vocabulary correctly, hosted in student's personal GitHub repo, README explains *when* to invoke and *why* it helps.

| # | Due | Capability | Required form | Brief |
|---|---|---|---|---|
| 1 | Sun 5/24 | **Skill** | `SKILL.md` with YAML frontmatter + body, in `~/.claude/skills/` or `.claude/skills/` | A skill that helps with your Sprint 1 work. Could be: "review my résumé draft for ATS compatibility", "lint my Ollama prompt", or anything that earns its keep. |
| 2 | Sun 6/7 | **Subagent** | Subagent definition (frontmatter `name`, `description`, `tools`) | A specialized subagent. Must serve a role you can articulate: a code reviewer for your stack, a PR checker, a doc-writer for skills you own. |
| 3 | Sun 6/21 | **Hook** | Hook definition (PreToolUse, PostToolUse, Stop, etc.) | A hook that automates something. Example: post-edit auto-formatter, pre-commit secret scanner, Stop-hook that prints a summary of session changes. |
| 4 | Sun 7/12 | **MCP integration** | MCP server (stdio or HTTP) connecting CC to a service | Connect Claude Code to an external service. Could be: a database, a browser, a REST API, the class Ollama endpoint, or something niche. |
| 5 | Sun 8/2 | **Plugin** | A plugin that bundles ≥2 of the prior artifacts and adds a `plugin.json` manifest | Package up your work into a single distributable plugin. Reuse what you've built. |

**Grading bar**: 6% per artifact, all-or-nothing per rubric criterion. No half-credit unless rubric explicitly grants it.

## 8. Hosted LLM infrastructure

The class LLM service is the infrastructure that supports Sprint 1 (default backend), Sprint 2 (optional), and Sprint 3 (optional). It is also a *teaching artifact*: students don't just consume it, they learn from its design.

### What the instructor provides

- **Endpoint**: `https://llm.uvucs.org` (or similar — exact URL TBD by instructor at infra setup time)
- **Backend**: Ollama on a CS department GPU server, hosting at least one model in the 70B-class range plus one fast 7B-class model for quick iterations
- **API auth**: per-student API key, issued upon Git username submission
- **Rate limits**: per-key request rate and concurrent-request caps. Exact limits sized to (class size × expected demo-day load) with margin
- **Reverse proxy / API gateway**: minimum LiteLLM or a small Express/FastAPI key-checker fronting Ollama
- **Status page**: a simple URL students can check before assuming the service is down
- **Outage policy**: published expected-uptime + how to fall back to Claude API during an outage (assignments designed to allow Strategy-pattern fallback)

### What students learn from using it

The hosted LLM is itself an instance of:
- **Service Activator** (EIP) — incoming requests trigger model inference
- **Adapter** (GoF) — wraps Ollama's native API as a stable HTTP contract
- **Perfect Framework: Security** — API keys, auth, rate limiting
- **Perfect Framework: Scale** — shared resource with quotas
- **Perfect Framework: Application > Workflow** — async / streaming response handling

Students name and discuss these in the W2 lecture and in their first reflection.

## 9. Vernacular reinforcement (no separate vocabulary track)

Vocabulary is enforced through *required output* in every graded artifact:

- **Sprint presentations**: rubric requires teams to name patterns, EIPs, Perfect Framework concerns. LLM grader verifies correct usage, not just mention.
- **CC artifacts**: SKILL.md / plugin descriptions must use CC vocabulary precisely (skill, subagent, hook, MCP, plugin, etc.).
- **Weekly lecture reflections**: each must apply ≥1 term from that week's lecture to current project work.
- **Individual sprint reflections**: each student names ≥3 patterns/EIPs/framework-elements they personally applied.

The LLM grader detects misuse: a student calling something a "hook" when it's actually a "skill" loses rubric points. A team naming "publish-subscribe" but actually implementing point-to-point loses rubric points.

## 10. Privacy & team visibility policy

Grade visibility within teams follows FERPA (Family Educational Rights and Privacy Act, 20 U.S.C. § 1232g) plus a deliberate pedagogical choice.

**Default rule.** Every student's grade and grade rationale is private. Students see only their own. The instructor and the LLM grader **never** disclose any student's grade or rationale to another student, including teammates.

**Voluntary self-disclosure is permitted.** A student may share their own grade or rationale with anyone they choose — that's their right under FERPA. The instructor neither facilitates nor obstructs this; no "share with team" feature is built into Canvas.

**Naturally visible work is not a grade.** Repositories, commits, pull requests, code-review comments, and demo videos are visible to all team members because they collaborate on them. This is collaboration, not grade disclosure, and is unaffected by this policy. In-sprint accountability happens via this visible work, not via after-the-fact grade comparison.

**Aggregate-only public metrics.** Class-level statistics (means, distributions, rubric-criterion histograms) may be shared without student names. Per-team aggregate metrics may be shared with that team only, without per-individual breakdown.

**No structured peer evaluation.** The course does not collect or distribute teammate-on-teammate evaluations. (Considered during design and rejected — the simpler default-private model is preferred.)

**LLM grader implications.** The grader's rationale-writing style is constrained to support this policy — see Section 6's "LLM grader rationale writing style." A rationale must be safe to forward to a teammate without revealing any FERPA-protected information about other students.

**Stated to students.** The Week 1 syllabus and the per-sprint Canvas modules will explicitly state the default-private rule and the right to self-disclose, so the policy is informed and unambiguous.

## 11. Submission mechanics & personal portfolio repos

**Submissions are git commits.** Across the course, individual deliverables are submitted by committing the artifact to a per-student portfolio repo and pasting the commit URL into Canvas. Team deliverables are submitted by tagging a specific commit SHA on the team repo as `sprint-{N}-final`. Canvas does not store artifacts directly; it stores commit URLs, and the LLM grader's plumbing pulls grading inputs from git.

**Per-student personal portfolio repo.** One repo per student, provisioned during W1 (see §4):

```
uvucs3660/portfolio_<github_username>_summer_2026
```

Standard structure (seeded by the starter template):

```
week1/
  git-training-cert.{pdf,png}
  pausch-reflection.md
  claude-pro-proof.png
  api-smoke-test.md
reflections/
  W02.md ... W13.md
cc-artifacts/
  01-skill/
  02-subagent/
  03-hook/
  04-mcp/
  05-plugin/
sprints/
  sprint-1-reflection.md
  sprint-2-reflection.md
  sprint-3-reflection.md
```

**Per-sprint team repo.** One repo per (project N, team M):

```
uvucs3660/project<N>_team<M>_summer_2026
```

Provisioned at sprint kickoff after team assignments are computed (see §6 Team generation).

**Why git-as-submission, not Canvas upload.**
- The LLM grader needs structured access to code, commit history, and review threads. Canvas file uploads obscure all of that.
- Industry submission patterns are git-based; the class teaches what students will see professionally.
- A single source of truth (the repo) is easier to grade fairly and audit later.
- Late-policy adjudication and version history are intrinsic to git.

**Permissions.** Students get `maintain` on their portfolio repo and on each team repo for which they're a member. The instructor (`hunterino`) gets `admin` on every repo in `uvucs3660`. The LLM grader uses a fine-grained personal access token scoped read-only to the org.

**LLM API keys.** Each student receives one personal API key for the class LLM service (issued during W1, rotatable on incident). The key is delivered via Canvas direct message and **never committed to any repo**. Keys are scoped to the student and used both for project work and for the W1 smoke test.

**Toolchain.** The instructor's `examples/gittools/` toolchain handles repo provisioning, collaborator management, and API key issuance. Inputs: roster JSON, sprint team assignments JSON. Outputs: idempotent shell scripts of `gh` CLI calls. The 2025 implementation exists and is the starting point; refactor for 2026 (including the no-repeat invariant verification) is an implementation-plan task.

## 15. Success criteria

The 2026 class is successful if, at the end:

- ≥80% of students can correctly name and explain ≥10 GoF patterns, ≥10 EIPs, ≥6 Perfect Framework concerns, and the full Claude Code capability vocabulary (skill, subagent, hook, MCP, plugin, agentic loop, context management, permission modes).
- Every team has shipped 3 sprints + every student has shipped 5 CC artifacts.
- Sprint 3 capstone projects are demonstrable to a non-CS3660 audience without remedial explanation.
- Individual grades are *defended* by LLM-grader rationale that students can read and challenge.
- Week 1 onboarding ≥95% completion (the API-key + Git-username gates make this enforceable).
